# Подключение тестовой CRM «Новая Реальность»

> **Только тестовая среда.** Этот комплект не подключён к Netlify-проекту `spiffy-kheer-42015a` и не содержит ключей от рабочей базы. Не подставляйте сюда production-ключи и реальные данные клиентов.

## Что добавлено в тестовый проект

- Supabase Auth: регистрация клиентов по email/паролю и вход сотрудников.
- Профили с ролями `customer`, `manager`, `admin`. Новая самостоятельная регистрация всегда получает только роль `customer`.
- Таблица `orders` и серверная функция `create_order`: заявка из Центра заказов сохраняется в БД, даже если клиент не зарегистрирован.
- Личный кабинет клиента: показывает только заявки, отправленные в момент авторизованной сессии этого клиента.
- Кабинет сотрудников: без входа рабочая область не открывается; менеджер получает только назначенные ему заявки; администратор — все заявки.
- Администратор может назначать и переназначать заявки, создавать учётные записи менеджеров и отключать/включать их доступ.
- Изменение статуса, приоритета и внутренней заметки выполняется серверной RPC-функцией с проверкой роли и назначения.
- Ключ `SUPABASE_SECRET_KEY` / `SUPABASE_SERVICE_ROLE_KEY` используется только Netlify Function и не отправляется браузеру.

## Шаг 1. Создайте отдельный проект Supabase

1. Откройте [Supabase](https://supabase.com/) и создайте новый проект именно для тестирования, например `novaya-realnost-test`.
2. Не подключайте проект Supabase, который уже обслуживает рабочие системы компании.
3. Дождитесь завершения создания проекта.
4. Откройте **SQL Editor → New query**.
5. Скопируйте целиком файл `supabase/migrations/202611090001_crm_core.sql`, вставьте в редактор и нажмите **Run**.

Скрипт создаёт таблицы, индексы, номера заявок, триггер создания клиентского профиля, функции CRM и ограничения доступа. Запускать его следует один раз на пустой тестовой базе.

## Шаг 2. Подготовьте локальные переменные

1. В корне папки проекта скопируйте `.env.example` в новый файл `.env`.
2. В Supabase откройте **Settings → API Keys**. Для новой тестовой базы используйте пару ключей нового формата.
3. Заполните в `.env`:
   - `SUPABASE_URL` — Project URL тестового проекта;
   - `SUPABASE_PUBLISHABLE_KEY` — публичный ключ с префиксом `sb_publishable_`;
   - `SUPABASE_SECRET_KEY` — секретный ключ с префиксом `sb_secret_`. Он нужен только серверной функции для создания учётных записей сотрудников.
4. Если в вашем проекте доступны только старые ключи, заполните вместо них `SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY` — код поддерживает оба формата.
5. Не присылайте secret/service-role key в чат, не вставляйте его в HTML/JS и не удаляйте `.env` из `.gitignore`.

`public-config` выдаёт браузеру только URL и публичный ключ. Secret/service-role key остаётся в окружении Netlify Functions. Не смешивайте ключи от разных проектов.

## Шаг 3. Запустите тестовый сайт локально

В терминале VS Code, находясь в корне этой папки, выполните:

```bash
npm install
npm install -g netlify-cli
netlify dev
```

Откройте локальный адрес, который покажет Netlify CLI (обычно `http://localhost:8888`). Для страниц кабинета и отправки заявки используйте именно этот адрес, а не `file://` и не Live Server: нужны локальные Netlify Functions.

В Supabase откройте **Authentication → URL Configuration** и добавьте локальный адрес в Redirect URLs, например:

```text
http://localhost:8888/**
```

Это нужно для подтверждения email и восстановления пароля.

## Шаг 4. Создайте первого администратора

Самостоятельная регистрация на `account.html` намеренно создаёт только клиента. Роль администратора нельзя выбрать в форме сайта.

1. Откройте `http://localhost:8888/account.html`.
2. Зарегистрируйте отдельный тестовый аккаунт администратора на свой email.
3. Если Supabase попросит подтверждение email, перейдите по ссылке из письма.
4. В Supabase откройте **SQL Editor** и выполните запрос, заменив адрес на тот же email:

```sql
update public.profiles
set role = 'admin'
where lower(email) = lower('ВАШ_EMAIL');
```

5. Откройте `http://localhost:8888/manager.html` и войдите с этим аккаунтом.

Храните доступ администратора отдельно от клиентских и менеджерских аккаунтов. Восстановить роль можно только из доверенной панели Supabase.

## Шаг 5. Добавьте менеджеров и проверьте CRM

1. В кабинете администратора откройте **Сотрудники**.
2. Создайте менеджера: имя, email и начальный пароль не короче 12 символов. Форма создаёт аккаунт сразу; письмо с паролем не отправляется — передайте пароль сотруднику безопасным способом.
3. Откройте `account.html` в другом браузере/приватном окне и создайте тестовый клиентский аккаунт либо оформите гостевой заказ без регистрации.
4. Добавьте позиции в корзину через каталог/конструктор, откройте Центр заказов и отправьте заявку. Обязательны имя и **хотя бы один** контакт: телефон или email.
5. Заявка появится у администратора как неназначенная. Откройте карточку заявки и назначьте менеджера.
6. Войдите менеджером в `manager.html`: он должен видеть только назначенные ему заявки.
7. Создайте вторую тестовую заявку и назначьте другому менеджеру. Первый менеджер не должен увидеть её, в том числе после закрытия/завершения.
8. Клиент, вошедший до отправки заявки, увидит её в личном кабинете. Гостевые заявки не привязываются к аккаунту задним числом.

## Границы текущей тестовой версии

- Файловые вложения пока не загружаются в хранилище: БД сохраняет только название, размер и MIME-тип. Реальную загрузку в приватный Supabase Storage добавим отдельно.
- Гостевая заявка сохраняется в CRM, но не показывается клиентскому кабинету, потому что у неё нет подтверждённого владельца аккаунта.
- Менеджер может обновлять статус, приоритет и внутреннюю заметку только у своей заявки. Назначение/переназначение доступно только администратору.
- Создание дополнительных администраторов в интерфейсе пока намеренно не предусмотрено. Первую/дополнительную роль admin назначает владелец базы через SQL Editor.
- Для публичной production-эксплуатации перед включением реальных клиентов нужно отдельно добавить защиту публичной формы от спама (например, CAPTCHA/rate limit), политику хранения персональных данных, резервное копирование и проверить настройки email/SMTP.
- Эта сборка не развёрнута и не привязана к `spiffy-kheer-42015a`.

## Переменные для будущего отдельного тестового Netlify-проекта

Когда локальные проверки пройдут, можно создать **новый** Netlify-проект, не связывая его с `spiffy-kheer-42015a`, и задать в нём те же переменные окружения. Для Netlify нужны `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY` и `SUPABASE_SECRET_KEY`. Для старого проекта допустимы `SUPABASE_ANON_KEY` и `SUPABASE_SERVICE_ROLE_KEY`. Не используйте кнопку Production deploy рабочего сайта.
